ТЗ ссылается на этот файл в §3.2 («в отчёт: фактическая частота обновлений,
латентность одиночной команды, джиттер») и в §8.4.

> **Статус: измерено на железе.** Pico W с прошивкой **1.0.2**, серийный номер
> `395E66CB37A863E6`. Все числа ниже получены на реальной плате
> (`tests/bringup_check.py`, `tests/counter.py`) и воспроизводятся командами из

## 1. Почему требование «≥500 кГц на линию» снято

Это арифметика, и она зафиксирована заказчиком в ТЗ §3.2.

Параллельный счётчик требует менять 24-битное слово на каждое приращение. Чтобы
получить 500 кГц на младшем бите, нужно ≥ 1 000 000 обновлений слова в секунду,
то есть ≥ 4 МБ/с полезных данных (по 4 байта на слово), плюс накладные расходы
кадрирования.

USB Full-Speed даёт 12 Мбит/с = 1.5 МБ/с на шине; bulk-трафик реально занимает
~0.7–1.0 МБ/с. Дефицит — **4–6×**. И RP2040, и RP2350 имеют только FS-USB,
поэтому задача не решается сменой МК.

Вместо порога: живой интерактивный доступ сохраняется полностью, а целевая
скорость — «максимально достижимая», она измеряется и документируется здесь.

## 2. Что измеряется

| Величина | Определение | Где считается |
|---|---|---|
| **Частота обновлений (устройство)** | `applied / (duration_us × 10⁻⁶)`, где `duration_us` — время цикла записи в SIO, измеренное **на устройстве** (`time_us_32()`) | `protocol.md` §4.10; `StreamResult.updates_per_second` |
| **Частота обновлений (тракт)** | то же по wall-clock всего прогона, включая USB и Python | `stream()` / `counter.py` |
| **Латентность round-trip** | время `set_pin` + `read_all` | `bringup_check.py`, фаза 7 |
| **Джиттер латентности** | распределение времени round-trip | там же (mean/median/p95/max) |
| **Межобновляемый джиттер** | интервалы между изменениями на захвате анализатора | `measure.py` — **не снят**, нет анализатора |

Разделение «устройство» / «тракт» важно: первое — предел петли записи в SIO,
второе — предел всего тракта ПК → USB → устройство.

## 3. Результаты

### 3.1 Сводка

| Величина | Значение |
|---|---|
| Частота обновлений, петля на устройстве | **1 640 000 /с** (30.5 мс на 50 000 значений) |
| Частота обновлений, полный тракт | **148 600 /с** |
| Полезный поток | **0.595 МБ/с** |
| Латентность round-trip: среднее | **0.637 мс** |
| Латентность: медиана | **0.604 мс** |
| Латентность: p95 | **0.878 мс** |
| Латентность: максимум | **1.032 мс** |
| Ошибки CRC за прогон (3 228 кадров) | **0** |
| Кадров с ошибкой | 2 (намеренно вызванные проверками ошибок) |

Прогон: 50 000 значений счётчика, 200 USB-транзакций по 250 значений.

### 3.2 Что дало ускорение

Исходно было **59 000 обновлений/с**. Узкие места снимались по одному, каждое
подтверждено измерением:

| Шаг | Изменение | Частота | Поток |
|---|---|---|---|
| 1.0.1 (исходно) | — | 59 000 /с | 0.236 МБ/с |
| 1.0.2 | OUT-эндпоинт вооружён на **целый кадр** (1088 Б) вместо одного 64-байтного пакета: запрос приходит одной USB-передачей, а не 16 | 67 000 /с | 0.268 МБ/с |
| хост | CRC через `binascii.crc_hqx` вместо побитового цикла на Python: **1.36 мс → 0.003 мс** на кадр 1 КБ (в 493 раза) | 114 000 /с | 0.457 МБ/с |
| хост | Конвейер глубиной 1: следующий блок пишется до чтения предыдущего ответа — минус один round-trip на блок (ТЗ §3.2, «минимум ожиданий round-trip») | **148 600 /с** | **0.595 МБ/с** |

Итого **2.5×** к исходному. Узкие места найдены счётчиками самой прошивки
(`docs/protocol.md` §9): `out_cb_count` на кадр показал 16 передач вместо одной,
а профилирование хоста — 1.36 мс на CRC.

### 3.3 Где предел

Запись 1024 байт на этом тракте стоит ≈1.3 мс, то есть ≈0.79 МБ/с — близко к
практическому потолку bulk на USB Full-Speed. При 250 значениях на кадр это даёт
теоретический максимум ≈190 000 обновлений/с; измеренные 148 600 — примерно 78 %
от него. Остаток — не полностью скрытая латентность ответа (конвейер глубиной 1).

Дальнейший рост требует либо более глубокого конвейера, либо кадров больше
1024 байт (запрещено протоколом §4.10), либо High-Speed, которого у RP2040 нет.

### 3.4 Чего не хватает

* **Межобновляемый джиттер по захвату анализатора** — не снят: анализатор не
  поднят (нет COM-порта). Инструмент готов: `tests/counter.py --capture` +
  `tests/measure.py`. До этого числа джиттера в отчёте отсутствуют, а не оценены
  «на глаз».
* **Джиттер по всему пути** — здесь есть только распределение латентности
  round-trip (таблица 3.1); это другой показатель.

## 4. Как воспроизвести

```powershell
# полная проверка железа, включая замеры (37 проверок)
.\.venv\Scripts\python.exe tests\bringup_check.py --json out.json

# только скорость, 3 прогона по 50 000 значений
.\.venv\Scripts\python.exe tests\counter.py --values 50000

# латентность интерактивного API
.\.venv\Scripts\python.exe tests\counter.py --mode manual --values 200

# с анализатором: паттерн + захват (.lac/.vcd) + отчёт о частоте и джиттере
.\.venv\Scripts\python.exe tests\counter.py --capture --port COM14 `
    --values 100000 --frequency 20000000 --trigger edge:1

# пересчёт по готовому захвату
.\.venv\Scripts\python.exe tests\measure.py <capture.lac> --json --markdown report.md
```

`measure.py` считает `rate_hz = 1 / mean(интервал)` — намеренно **не**
`changes / span`, потому что последняя формула на N изменениях считает N событий
там, где интервалов N−1, и завышает результат на `N/(N−1)`. Альтернативная оценка
приводится рядом как `span_rate_hz`, чтобы расхождение было видно. Джиттер:
`jitter_pp_us` (max−min), `jitter_rms_us` (σ), `cv_percent`.

По умолчанию анализируется **пост-триггерная** область (`--region post`): до
триггера линии делают что угодно, и это исказило бы частоту.

> ТЗ §5.2 прямо говорит: автоматической сверки с ожидаемой последовательностью
> **нет**. `measure.py` — измерение, а не проверка корректности.

## 5. Ограничения стенда

* 24-канальный режим анализатора: буфер 32768 сэмплов, pre ≤ 3276, макс. 100 МГц.
* `TerminalCapture capture` блокируется до триггера **без таймаута**;
  `tests/analyzer.py` запускает его фоном с дедлайном и после kill обязательно
  делает abort/reopen, иначе устройство остаётся «заряженным».
* Декодеры протоколов в GUI не работают (несовместимость ABI Python 3.14).
  Разбор — из `.vcd` в PulseView/`sigrok-cli`; ни то, ни другое здесь не
  установлено.
