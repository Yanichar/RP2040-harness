## Соответствие логическим индексам

Прошивка адресует линии логическими индексами 0…23 (`docs/protocol.md` §3).
Порядок в таблице — это и есть порядок индексов:

`GP2` = индекс 0 → `PA0`, `GP3` = индекс 1 → `PA1`, …, `GP28` = индекс 23 → `PD7`.

Отсюда же номера каналов для `TerminalCapture` / `tests/measure.py`
(каналы там **1-based**, в `.lac`/`.tcs` — **0-based**):

| Порт | Входы | Каналы (1-based) |
|---|---|---|
| PA | PA0…PA7 | 1…8 |
| PB | PB0…PB7 | 9…16 |
| PD | PD0…PD7 | 17…24 |

То есть `PA0` = канал 1, `PB0` = канал 9, `PD0` = канал 17, `PD7` = канал 24.

## Статус

**Разводка подтверждена заказчиком и ПРОВЕРЕНА ИЗМЕРЕНИЕМ.**

Проверка выполнена не анализатором, а двумя независимыми harness'ами,
подключёнными к одним и тем же 24 проводам (`tests/cross_harness.py`):

1. RP2040 гонит, кипарис читает — по очереди поднимается каждая из 24 линий,
   кипарис должен увидеть ровно этот бит;
2. кипарис гонит, RP2040 читает — то же в обратную сторону;
3. перед каждой фазой читатель переводится в INPUT, чтобы платы не бодались.

Обе фазы прошли без расхождений на всех 24 линиях:

```
PASS: both harnesses verified each other on all 24 lines, both directions
```

Это доказывает, что индекс `N` — одна и та же физическая линия на обеих платах,
и что разводка `GP2…GP28 → PA0…PD7` верна.

Оговорка: соответствие входов `PA/PB/PD` **номерам каналов** в ПО анализатора
(`PA0`=1 … `PD7`=24, таблица выше) этой проверкой не затрагивалось — она
относится к нумерации `TerminalCapture`, а не к электрике.

## Прочее

* GP0/GP1 RP2040 — отладочный UART, в 24 линии не входят.
  GP23/GP24/GP25/GP29 заняты платой Pico W (CYW43 / VBUS sense / LED / VSYS).
* Триггер для сценария счётчика: индекс 0 → `PA0` → канал 1, поэтому
  `tests/counter.py --capture --trigger edge:1` (значение по умолчанию).
* 24-канальный режим анализатора: буфер 32768 сэмплов, max pre 3276,
  max post 32766.
