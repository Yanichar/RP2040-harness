# RP2040 Harness — протокол обмена (v1.0)

Статус: **зафиксирован** для реализации v1.0. Пункты, требующие подтверждения
заказчика, помечены ❓ и перечислены в конце.

Документ — единственный источник истины для `firmware/` и `host/`. Любое
расхождение между прошивкой и хостом считается багом прошивки/хоста, а не
документа.

---

## 1. Транспорт

* USB Full-Speed (12 Мбит/с), raw vendor-класс.
* Интерфейс **0** — данные:

  | Параметр | Значение |
  |---|---|
  | `bInterfaceClass` | `0xFF` (vendor specific) |
  | `bInterfaceSubClass` | `0x48` (`'H'`) |
  | `bInterfaceProtocol` | `0x01` |
  | Bulk OUT | `0x01` (host → device), `wMaxPacketSize = 64` |
  | Bulk IN | `0x81` (device → host), `wMaxPacketSize = 64` |

* Интерфейс **1** — reset-интерфейс Pico SDK (для `picotool`):

  | Параметр | Значение |
  |---|---|
  | `bInterfaceClass` | `0xFF` |
  | `bInterfaceSubClass` | `0x00` (`RESET_INTERFACE_SUBCLASS`) |
  | `bInterfaceProtocol` | `0x01` (`RESET_INTERFACE_PROTOCOL`) |
  | Endpoints | нет |

  `picotool reboot -f -u` использует именно его.

* Все многобайтовые поля — **little-endian**.
* Обмен строго «запрос → ответ»: устройство отвечает ровно одним кадром на
  каждый корректный кадр запроса, в порядке поступления. Исключение —
  опкод `STREAM`, который обрабатывается дольше, но всё равно даёт один ответ.

## 2. Кадрирование

### 2.1 Кадр запроса (host → device)

```
 смещ  размер  поле
   0      1    magic    = 0xA5
   1      1    opcode
   2      2    seq      сквозной счётчик хоста, эхо в ответе
   4      2    len      длина payload в байтах (0..1024)
   6      2    crc      CRC-16/CCITT-FALSE
   8    len    payload
```

### 2.2 Кадр ответа (device → host)

```
 смещ  размер  поле
   0      1    magic    = 0x5A
   1      1    status   код ошибки (§2.4)
   2      2    seq      копия seq запроса
   4      2    len      длина payload в байтах
   6      2    crc      CRC-16/CCITT-FALSE
   8    len    payload
```

### 2.3 CRC

**CRC-16/CCITT-FALSE**: `poly = 0x1021`, `init = 0xFFFF`, `refin = false`,
`refout = false`, `xorout = 0x0000`.

Считается по байтам кадра `[1 .. 6)` (то есть `opcode, seq, len`) с
последующим продолжением по всем байтам `payload`. Байт `magic` и сами байты
CRC в расчёт не входят.

Контрольный вектор: `CRC16("123456789") = 0x29B1`.

### 2.4 Коды статуса ответа

| Код | Имя | Смысл |
|---|---|---|
| `0x00` | `OK` | успех |
| `0x01` | `ERR_UNKNOWN_OPCODE` | опкод не поддерживается |
| `0x02` | `ERR_BAD_LENGTH` | `len` не соответствует опкоду |
| `0x03` | `ERR_BAD_PARAM` | пин вне диапазона, недопустимое значение поля |
| `0x04` | `ERR_BUSY` | устройство занято (например, идёт `STREAM`) |
| `0x05` | `ERR_CRC` | CRC кадра запроса не совпал |
| `0x06` | `ERR_MAGIC` | неверный `magic` |

При `status != 0` payload ответа пуст, если в описании опкода не сказано иное.

### 2.5 Границы и восстановление

* Максимальная длина payload запроса — **1024 байта** (кадр ≤ 1032 байта).
* Максимальная длина payload ответа — **1024 байта**.
* Кадр **длино-ограниченный**: устройство собирает кадр по полю `len`, а не по
  границам USB-пакетов.
* OUT-эндпоинт вооружён на **целый кадр** (1088 байт), поэтому запрос приходит
  одной USB-передачей, а не 16 пакетами. Передача завершается коротким пакетом;
  если длина кадра кратна 64, короткого пакета нет, и **хост обязан дослать
  zero-length packet**. Без этого устройство продолжит ждать данные.
* Ответ завершается коротким пакетом. Если полная длина ответа кратна 64,
  устройство досылает **zero-length packet**, иначе хост не увидел бы конец
  передачи.
* При неверном `magic` или `len > 1024` приёмный автомат сбрасывается, и
  устройство отвечает кадром `ERR_MAGIC` / `ERR_BAD_LENGTH` с `seq = 0`,
  после чего снова ищет `magic`.
* Таймаут ответа на стороне хоста — **1000 мс** по умолчанию (настраивается).

### 4.1 `info_t` — ответ `GET_INFO` (32 байта)

| Смещ | Размер | Поле | Значение |
|---|---|---|---|
| 0 | 1 | `proto_major` | `1` |
| 1 | 1 | `proto_minor` | `0` |
| 2 | 1 | `fw_major` | версия прошивки |
| 3 | 1 | `fw_minor` | |
| 4 | 1 | `fw_patch` | |
| 5 | 1 | `pin_count` | `24` |
| 6 | 2 | `reserved` | `0` |
| 8 | 4 | `caps` | битовая маска возможностей (§4.2) |
| 12 | 4 | `pin_mask` | `0x00FFFFFF` — какие логические индексы реализованы |
| 16 | 8 | `board_id` | уникальный ID платы (flash unique id) |
| 24 | 4 | `reset_iface` | `1` — номер reset-интерфейса |
| 28 | 4 | `reserved` | `0` |

### 4.2 Биты `caps`

| Бит | Имя | Смысл |
|---|---|---|
| 0 | `PIN_DIR` | смена INPUT/OUTPUT |
| 1 | `PULL` | pull-up / pull-down |
| 2 | `OPEN_DRAIN` | open-drain |
| 3 | `DRIVE_STRENGTH` | 2/4/8/12 мА |
| 4 | `SLEW` | slow/fast |
| 5 | `SCHMITT` | Schmitt trigger |
| 6 | `ATOMIC_MASK` | `SET_MASK` |
| 7 | `STREAM` | `STREAM` |
| 8 | `BATCH` | `SET_MANY` / `CONFIGURE_MANY` |
| 9 | `RESET_IFACE` | reset-интерфейс для `picotool` |

Для v1.0 `caps = 0x000003FF`.

### 4.3 `pin_state_t` — ответ `GET_PIN` (8 байт)

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 1 | `index` |
| 1 | 1 | `dir` — `0` = INPUT, `1` = OUTPUT |
| 2 | 1 | `level` — текущий логический уровень на площадке (0/1) |
| 3 | 1 | `flags` (§4.5) |
| 4 | 1 | `drive` (§4.6) |
| 5 | 1 | `slew` — `0` = slow, `1` = fast |
| 6 | 2 | `reserved` |

### 4.4 `cfg_pin_t` — `CONFIGURE_PIN` / `CONFIGURE_MANY` (8 байт)

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 1 | `index` — `0..23` |
| 1 | 1 | `dir` — `0` = INPUT, `1` = OUTPUT |
| 2 | 1 | `flags` (§4.5) |
| 3 | 1 | `drive` (§4.6) — применяется только к `dir = 1` |
| 4 | 1 | `slew` — `0` = slow, `1` = fast |
| 5 | 1 | `level` — уровень, выставляемый при `dir = 1` |
| 6 | 2 | `reserved` |

Семантика: конфигурация применяется целиком за одну операцию. Если
`dir = 0`:

* поля `drive`, `slew` **проверяются на допустимость, но игнорируются** — линия
  сохраняет ранее установленные значения (они снова начнут действовать при
  переводе в `OUTPUT`);
* поле `level` игнорируется, выходная защёлка линии принудительно обнуляется;
* `flags` (включая Schmitt и подтяжки) применяются всегда.

Значения вне диапазона → `ERR_BAD_PARAM`, пин не изменяется.
Если `dir = 1`, все поля применяются.

### 4.5 `flags`

| Бит | Имя | Смысл |
|---|---|---|
| 0 | `PULL_UP` | подтяжка к 3.3 В |
| 1 | `PULL_DOWN` | подтяжка к GND |
| 2 | `OPEN_DRAIN` | open-drain (только при `dir = 1`) |
| 3 | `SCHMITT` | Schmitt trigger включён |

`PULL_UP` и `PULL_DOWN` одновременно — `ERR_BAD_PARAM`. Оба сняты — «без
подтяжки». Биты `4..7` должны быть нулевыми, иначе `ERR_BAD_PARAM`.

### 4.6 `drive`

| Значение | Ток |
|---|---|
| `0` | 2 мА |
| `1` | 4 мА |
| `2` | 8 мА |
| `3` | 12 мА |

Иные значения → `ERR_BAD_PARAM`.

### 4.7 `set_pin_t` — `SET_PIN` / `SET_MANY` (4 байта)

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 1 | `index` |
| 1 | 1 | `level` — `0` или `1` |
| 2 | 2 | `reserved` |

Пин должен быть сконфигурирован как `OUTPUT`; если он `INPUT`, возвращается
`ERR_BAD_PARAM` (неявное переключение направления запрещено).

### 4.8 `set_mask_t` — `SET_MASK` (8 байт)

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 4 | `mask` — какие биты менять |
| 4 | 4 | `value` — новые значения для битов, отмеченных в `mask` |

Применяется **атомарно**: одно защёлкивание SIO-регистра, без промежуточных
состояний. Бит `i` затрагивается только если выставлен в `mask`; остальные
линии сохраняют прежнее значение.

Пины, попавшие в `mask`, но не сконфигурированные как `OUTPUT`, игнорируются
(значение защёлкивается в SIO, но на площадку не влияет до перевода в
`OUTPUT`). Ответ — `u32 applied_value` = фактическое состояние 24 выходных
защёлок после операции.

### 4.9 `READ_ALL`

Возвращает `u32`, где бит `i` — текущий логический уровень пина с индексом `i`
(значение читается из SIO `GPIO_IN`, то есть для OUTPUT-пина это то, что
реально на площадке).

### 4.10 `STREAM` — максимальная скорость

Payload запроса:

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 4 | `mask` — какие линии переключать |
| 4 | 4 | `count` — число следующих `u32` (`1..250`) |
| 8 | 4 | `mode` — `0` = обычный; зарезервировано, должно быть `0` |
| 12 | 4 | `reserved` |
| 16 | `4*count` | `values[]` |

Устройство применяет `values[i]` друг за другом с максимально возможной
скоростью: `SIO->GPIO_OUT = (prev & ~mask) | (values[i] & mask)` — по одной
атомарной записи на элемент. Никакого USB-обмена внутри цикла не происходит.

Payload ответа `stream_rep_t`:

| Смещ | Размер | Поле |
|---|---|---|
| 0 | 4 | `applied` — сколько значений реально записано |
| 4 | 4 | `duration_us` — длительность цикла по `time_us_32()` |
| 8 | 4 | `toggles` — число изменений состояния на линиях маски (для контроля) |
| 12 | 4 | `reserved` |

`count = 0` или `mask = 0` → `ERR_BAD_PARAM`. `count > 250` →
`ERR_BAD_PARAM` (кадр не влезает в 1024 байта: `16 + 4·250 = 1016`).

Частота обновления вычисляется хостом как `applied / (duration_us × 1e-6)`.

### 4.11 `status_t` — ответ `GET_STATUS` (24 байта)

| Смещ | Размер | Поле | Смысл |
|---|---|---|---|
| 0 | 1 | `state` | `0` = idle, `1` = streaming |
| 1 | 1 | `last_status` | статус последнего обработанного кадра |
| 2 | 2 | `reserved` | |
| 4 | 4 | `frames_ok` | счётчик успешных кадров |
| 8 | 4 | `frames_err` | счётчик кадров с ошибкой |
| 12 | 4 | `crc_errors` | |
| 16 | 4 | `uptime_ms` | время с запуска |
| 20 | 4 | `reserved` | |

## 5. Поведение и безопасность

### 5.1 Состояние после boot/reset

Все 24 линии — **INPUT, без подтяжек**, Schmitt trigger по умолчанию
(аппаратный сброс RP2040 даёт Schmitt включённым), drive strength аппаратный
по умолчанию (4 мА), slew slow. Прошивка явно приводит все 24 линии в
`INPUT` + `pull = none` **до** инициализации USB.

### 5.2 Потеря связи с ПК

Прошивка переводит все 24 линии в `INPUT` без подтяжек (open-drain снят),
сбрасывает приёмный автомат кадров и останавливает `STREAM`.

**На реальной плате это делает обработчик `tud_suspend_cb`, а не
`tud_umount_cb`.** Причина аппаратная: у RP2040 нет детектора VBUS, и TinyUSB
собирается с `FORCE_VBUS_DETECT=1` — при этом `DCD_EVENT_UNPLUGGED` (и,
следовательно, `tud_umount_cb`) вообще не генерируется, а состояние «хост
отключён» и «шина в suspend» неразличимы. `tud_umount_cb` оставлен как
безопасная ветка, но на этом МК он мёртвый код.

Следствия (осознанные, требование ТЗ §3.4 — безопасность важнее удобства):

*suspend* → все линии в `INPUT` без подтяжек;
* конфигурация **не** восстанавливается при *resume* — хост должен применить её
  заново;
* шина уходит в suspend только когда хост действительно перестаёт её вести
  (≥ 3 мс полного простоя: отключение, сон машины, снятие питания порта). Пока
  сессия жива, SOF-пакеты идут каждую миллисекунду, поэтому в обычной
  интерактивной работе и во время `STREAM` этого не происходит.

### 5.3 Эксклюзивный доступ

Протокол не содержит механизма арбитража: устройство обслуживает один
интерфейс. Эксклюзивность обеспечивается на стороне ПК файловой блокировкой
(`host/`, §4.3 ТЗ). Второй процесс получит `ERR_BUSY`-подобную ошибку
открытия на хосте.

### 5.4 Прочее

* 5 В на линии не подавать.
* Open-drain использовать только с внешними подтяжками.

Устройство отдаёт BOS-дескриптор с Microsoft OS 2.0 descriptor set,

`CompatibleID = "WINUSB"` и registry-свойством `DeviceInterfaceGUID`:

| Интерфейс | GUID |
|---|---|
| 0 (данные) | `{7f0d2b1a-4c6e-4a2f-9d31-5b7c8e0f1a22}` |

Запрос `GET_MS_DESCRIPTOR` (`bmRequestType = 0xC0`, `bRequest = 1`,
`wIndex = 7`) обслуживается прошивкой.

## 9. Диагностика и восстановление (EP0)

Bulk-эндпоинты могут «замолчать» — например, если хост закрыл WinUSB-хэндл с
активным OUT-запросом: Windows посылает `CLEAR_FEATURE(ENDPOINT_HALT)`, и
TinyUSB сбрасывает признак занятости, **не вызывая** callback драйвера.
Прошивка самовосстанавливается (главный цикл переводит эндпоинт в armed
состояние, спрашивая состояние у стека, а не у своей теневой переменной), но на
случай любой другой рассинхронизации есть канал управления, который работает
всегда, пока устройство перечислено:

| Запрос | `bmRequestType` | Данные | Смысл |
|---|---|---|---|
| `0x42` `GET_STATE` | `0xC0` | IN, 76 Б | снимок внутреннего состояния USB-слоя |
| `0x43` `REARM` | `0x40` | нет | принудительно вооружить OUT-эндпоинт |

Это вендорские запросы к устройству, вне bulk-протокола. Читаются утилитой
`tests/harness_diag.py`. Структура `GET_STATE`:

| Смещ | Поле |
|---|---|
| 0 | `magic` = `0xA5`, `version`, `struct_len` (`u16`) |
| 4 | `tud_ready`, `tud_mounted`, `itf_num`, `ep_in`, `ep_out`, `out_armed`, `out_hw_busy`, `tx_busy`, `tx_in_zlp`, `rx_have`, `last_result`, резерв |
| 16 | 15 счётчиков `u32`: `init_count`, `open_count`, `reset_count`, `out_cb_count`, `in_cb_count`, `out_rearm_ok`, `out_rearm_fail`, `in_start_ok`, `in_start_fail`, `in_dropped`, `rx_bytes`, `frames_ok`, `frames_err`, `crc_errors`, `uptime_ms` |

`out_armed` берётся из состояния стека (`usbd_edpt_busy`), а не из теневой
переменной драйвера.
